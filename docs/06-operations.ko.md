폰 서버에는 랙 서버에 없는 소모품이 둘 있다. 닳는 배터리와, 팬이 없는 케이스다. 이 문서의
모든 것은 그 둘이 실험을 끝내지 못하게 하려고, 그리고 인상 대신 수치를 남기려고 있다.

## 6.1 닳는 부품은 배터리다

안드로이드 9에는 충전 상한 설정이 없다. 꽂아 두면 하루 24시간을 100%에서 보낸다. 2017년
배터리에 이 말은 1~2년 안에 부푼다는 뜻이고, 사람이 없는 곳에 두는 기기의 부푼 배터리는
성능 이야기가 아니라 실제 위험이다.

루팅 없이 쓸 수 있는 수단은 둘이다. 충전기를 켜고 끄는 스마트 플러그, 그리고 사람에게
그렇게 해 달라고 부탁하는 알림이다. `termux/battery-watch.sh`는 Termux 쪽에서 5분마다 sysfs를
읽는 반복으로 돈다(알림이 Termux:API를 지나기 때문이다). 작업 4247번과 부팅 스크립트는 반복이
죽었으면 다시 띄우기만 한다. 플러그가 설정돼 있으면 플러그를 쓴다([아래](#알림-대신-스마트-플러그)).

```sh
SYS=/sys/class/power_supply/battery
INTERVAL=300 # 반복에서 읽는 간격(초)
HIGH=80      # 충전 중 이 값 이상이면 충전기를 끈다(또는 빼라고 알린다)
PLUG_ON=40   # 방전 중 이 값 이하면 충전기를 켠다
LOW=30       # 방전 중 이 값 이하면 꽂으라고 알린다: 플러그가 도와주지 못한 경우다
```

찾는 데 시간이 든 구현 세부가 둘 있다.

- **SELinux 때문에 sysfs 디렉터리는 목록을 볼 수 없다.** 그러나 안의 개별 파일은 읽힌다.
  나열하려 하지 말고 `capacity`, `status`, `temp`, `current_now`, `voltage_now`를 이름으로
  읽는다.
- **히스테리시스를 넣는다.** 배터리가 정확히 80%에 머물면 15분마다 영원히 알림이 온다.
  임계값에서 5포인트 멀어져야 정상 상태로 돌아가게 했다.
- **낮은 쪽 알림은 진동도 울린다.** 안드로이드 알림 진동은 자다가 놓치기 쉽고 방해 금지
  모드가 아예 꺼 버린다. 그래서 LOW 분기에서 `termux-vibrate -d 600 -f`를 세 번 부른다.
  `-f`는 무음 모드에서도 울리게 하는 옵션이다. 배터리가 다 닳으면 서버가 같이 멈추지만
  가득 찬 배터리는 수명이 줄 뿐이라, 깨어날 만한 쪽은 아래쪽 하나다.

실행마다 한 줄이 쌓이고, 로그는 512KB에서 직접 회전시킨다.

```
2026-09-20 21:15:02 KST pct=80 status=Charging temp=31.5 mA=-412 mV=4301
```

알림이 도착한 모습이다. Termux의 웨이크 락, Tailscale의 연결 상태와 나란히 떠 있다. 이 세
알림이 함께 보이면 서버가 정상이라는 뜻이다.

![80%에서 충전기를 빼라고 알리는 Termux:API 알림](images/shot-battery-alert.png)

이 로그가 전력에 관한 질문에 답할 수 있게 해 준다. 실제 부하에서의 충전·방전 속도와, 그때
폰이 얼마나 뜨거운지다.

### 알림 대신 스마트 플러그

알림은 깨어 있는 사람이 있어야 쓸모가 있다. 2026-09-26 밤, 폰은 충전기 없이 밤을 넘겼다.
30% 이하의 첫 기록은 03:28에 나왔고, 09:45에 0%를 기록했고, 서버는 1시간 46분 동안 멈췄다.
기준값을 낮춰도 소용없었을 이유도 로그에 있다. 밤에 배터리로 돌 때는 안드로이드의 Doze가
15분 주기 작업의 간격을 1시간 54분에서 3시간 8분까지 늘렸고, 그동안 배터리는 한 시간에
5%쯤 떨어졌다(01:56에 36%, 05:56에 15%).

그래서 충전기를 TP-Link **Tapo P100**에 물리고, 감시 스크립트가 플러그를 켜고 끄게 했다.
충전 중 80%면 끄고, 방전 중 40%면 켠다. 30%가 아니라 40%인 까닭은 점검이 두 시간 늦게
와도 여유를 남기기 위해서다.

한 번만 하면 되는 설정이다.

1. Tapo 앱에서 플러그를 2.4GHz 와이파이에 연결하고 **Tapo Lab → 타사 호환성(Third-Party
   Compatibility)**을 켠다. 최신 펌웨어는 이것이 꺼져 있으면 로컬 제어를 거부한다.
   안전장치로 **켜고 끄는 예약**을 건다. 여기서는 08:00~08:45, 15:00~15:45, 22:00~22:45이고,
   근거는 아래 '사흘째'에 있다. 폰이 플러그를 조종하지 못하게 돼도 배터리가 대략 40~85%
   사이를 오간다. 나중에 플러그가 403으로 답하면 타사 호환성을 끄고, 10초 기다렸다가 다시 켠다.
2. 공유기에서 플러그의 주소를 고정한다. 선택 사항이다. 플러그가 다른 주소로 옮겨 가면
   도구가 브로드캐스트로 다시 찾는다. 다만 플러그가 집 안 네트워크에서 아예 대답하지 않게
   되면 브로드캐스트도 소용없다. 사흘째에 그런 일이 있었다.
3. [python-kasa](https://github.com/python-kasa/python-kasa)를 우분투 `python3`의 venv에
   설치한다. Termux의 `python3`는 플랫폼이 `android-24-arm64_v8a`인데, python-kasa가
   쓰는 `cryptography`는 이 플랫폼용 휠을 내지 않는다(`aiohttp`는 낸다). 그러면 pip가
   폰에서 Rust로 직접 컴파일해야 한다.

   ```bash
   apt-get install -y python3 python3-venv
   python3 -m venv /root/.local/share/tapo-venv
   /root/.local/share/tapo-venv/bin/pip install python-kasa==0.10.2
   ```

4. Tapo 계정을 어느 저장소에도 속하지 않는 곳에, 본인만 읽을 수 있게 저장하고, 플러그가
   대답하는지 확인한다.

   ```bash
   mkdir -p /root/.config/tapo
   nano /root/.config/tapo/credentials      # 1줄: 이메일, 2줄: 비밀번호
   chmod 600 /root/.config/tapo/credentials
   echo 192.168.0.42 > /root/.config/tapo/host
   /root/tapo_plug.py status                 # on | off
   ```

P100(하드웨어 2.0, 펌웨어 1.2.5)을 상대로 재 보고 알게 된 것이다.

- **패킷을 잃는다.** 폰에서 핑 60번을 보내 보니 공유기까지는 1%, 플러그까지는 15%를 잃었다.
  신호 세기는 −52dBm으로 좋았다. 어떤 요청이든 멈출 수 있으므로
  [`tapo_plug.py`](../tapo_plug.py)는 꼭 필요한 것만 보낸다. KLAP 핸드셰이크 두 번과 질의
  한 번이다. 요청마다 12초 타임아웃을 두고 최대 네 번 다시 시도한다. python-kasa의 보통
  방식인 `Device.connect()`는 기능 목록부터 전부 묻는데, 이 방식으로는 상태 읽기 다섯 번 중
  세 번 성공했다. 요청 세 개만 보내자 여덟 번 모두 성공했고, 0.1초에서 13초가 걸렸다.
- **python-kasa의 HTTP 세션을 그대로 쓴다.** 세션을 직접 넘기면 IP 주소에서 온 쿠키를 받는
  쿠키 저장소도 함께 줘야 한다. aiohttp의 기본 저장소는 이를 버리고, 세션 쿠키가 없으면
  플러그는 두 번째 핸드셰이크에 400으로 답한다. 처음에는 연결 재사용을 의심했지만 원인이
  아니었다. 쿠키를 제대로 보내고 비교하니 유지한 연결은 두 번째 핸드셰이크를 8번 중 6번,
  새 연결은 4번 통과했다.
- **플러그가 아니라 폰을 믿는다.** 전환이 이미 일어난 뒤에도 응답은 사라진다. 그래서 감시
  스크립트는 30초 안에 폰 자신의 `status`가 `Discharging`이나 `Charging`으로 바뀌었는지
  확인하고, 바뀌지 않았을 때만 위의 알림으로 돌아간다. 첫 자동 전환의 기록이다. 플러그의
  응답은 오는 길에 사라졌다.

  ```
  2026-09-27 15:10:48 KST plug off: phone now Discharging (plug said: error: no answer from the plug at 192.168.0.42 (KasaException))
  ```

두 번의 실행이 동시에 플러그를 바꾸지 않도록 잠금을 둔다. 이 작업이 같은 초에 두 번
시작되는 것을 로그에서 본 적이 있다.

이튿날 세 가지를 더 알게 됐다.

- **15분 작업은 밤에 시계가 되지 못한다.** 배터리로 돌 때 Doze가 작업 4247을 06:35부터
  12:03까지 미뤘다(5시간 28분). 그동안 배터리는 52%에서 25%로 내려갔고 40% 켜기는 돌지
  못했다. 같은 밤 proot 안의 감시 데몬은 오래 도는 반복인데, 20초도 멈추지 않았다. 멈추면
  하트비트 검사가 다운타임을 기록하는데 기록이 없다. 그래서 읽기를 5분마다 도는 반복으로
  옮기고, 작업은 반복을 되살리기만 하게 했다.
- **플러그가 거부할 수 있다.** 아홉 시간 동안 플러그는 첫 핸드셰이크에 403으로 답했고 아무것도
  바꾸지 않았다. 펌웨어는 그대로였다. Tapo 앱에서 타사 호환성을 껐다 켜자 끝났다. 이제
  `tapo_plug.py`는 재시도하는 대신 그렇게 말하고, 감시 스크립트는 그 해결법을 담은 알림을 곧바로
  띄운다. 플러그가 아예 대답하지 않을 때는 3번 연속일 때 띄우고, 다시 대답하면 지운다.
- **자동 끄기는 켜지 않는다.** 플러그는 켜진 뒤 정해진 시간이 지나면 스스로 꺼질 수 있어서,
  폰이 끄지 못해도 충전을 멈추게 할 수 있다. 하지만 켜는 예약이 하루 한 번뿐이면, 위와 같은
  거부가 있을 때 충전기가 꺼진 채 남아 폰이 방전된다. 서버에는 몇 시간 100%에 있는 것보다 그쪽이
  더 나쁘다. (사흘째부터는 켜기 예약이 하루 세 번이고, 각각 끄기 예약과 짝을 이룬다. 자동 끄기
  타이머는 여전히 쓰지 않는다.)

사흘째에 네 가지를 더 알게 됐다.

- **거부는 다시 온다.** 07:15부터 켜기 시도 55번이 모두 거부(403)됐고, 12:16에 풀렸다.
  그사이 배터리는 13%까지 내려갔다. 같은 토글로 풀렸다. 이틀 새 두 번이고, 펌웨어는
  그대로였으며, 원인은 아직 모른다.
- **앱으로는 되는데 폰에서는 플러그가 안 보일 수 있다.** 21:10부터 폰은 저장된 주소에서
  `Cannot connect to host`를 받았다. 단순 TCP 연결은 `No route to host`였고, 브로드캐스트
  검색에도 아무것도 잡히지 않았다. 그런데 Tapo 앱으로는 문제없이 켜고 껐다. 앱은 TP-Link
  클라우드를 거치는데 플러그가 그 연결은 유지하고 있었으니, 집 안 통신만 멈춘 것이다.
  플러그를 뽑았다가 다시 꽂자 네트워크에는 돌아왔다. 하지만 403으로 거부하는 상태였고,
  토글이 한 번 더 필요했다.
- **알림이 실패의 종류를 말한다.** 거부는 곧바로, 안 보임과 응답 없음은 각각 3번 연속일 때
  서로 다른 문구로 알린다. 모든 알림은 "앱에서 직접 켜고 끄기"로 시작한다. 안 보일 때는 앱의
  기기 정보와 비교하도록 저장된 주소를 보여 준다. 충전기를 켜지 못했을 때는 연료 게이지의
  평균 전류(`charge_counter / current_avg`)로 방전까지 남은 시간을 덧붙인다.
- **안전장치 예약은 로그에서 나왔다.** 배터리로 돌 때 폰은 쉴 때 시간당 약 4%, 에이전트가
  작업할 때 7~18%, 빌드 중에는 20~25%를 썼다. 80% 아래에서는 분당 약 1%씩 충전됐다. 하루
  세 번, 45분씩 켜면(한 번에 약 +45%) 조용하거나 가볍게 쓰는 날은 예약만으로 버틴다. 간격은
  6~9시간이다. 폰이 조종할 수 있을 때는 5분 안에 예약을 바로잡는다(80%에서 끄기, 40%에서
  켜기). 규칙은 폰에서 로컬 API(`add_schedule_rule`)로 넣었다. 대답이 여러 번 사라졌으므로,
  보낼 때마다 목록을 다시 읽고(`get_schedule_rules`) 없을 때만 다시 보냈다. 규칙은 하나씩만
  들어갔다.

## 6.2 열

팬이 없고, 케이스를 씌웠고, 충전 중이고, 부하가 걸렸다면 폰은 스로틀링한다. 똑똑한 방법보다
이 셋이 더 낫다.

- **케이스를 벗긴다.** 뒷판이 방열판이다.
- **화면은 꺼 두고 밝기는 낮춘다.** 디스플레이가 가장 큰 단일 전력 소모원이고 상당한
  발열원이다.
- **100% 충전 상태에서 무거운 작업을 돌리지 않는다.** 충전 자체가 발열이다. 고속 충전 중에
  사이트를 빌드하는 것이 최악의 조합이다.

CPU 센서보다 배터리 로그의 `temp`를 본다. `proot` 안에서는 thermal zone을 안정적으로 읽을
수 없고, 배터리의 서미스터는 내가 내려야 할 판단 — "이대로 계속하기에 너무 뜨거운가" —
에는 충분히 가깝다.

## 6.3 메트릭 엔드포인트

`serve_blog.py`는 `/api/metrics`를 제공한다. 대시보드의 유일한 데이터 출처다.

```bash
curl -s http://127.0.0.1:8080/api/metrics | python3 -m json.tool | head -30
```

CPU 사용률, 메모리와 스왑, 배터리 잔량과 상태, 온도, 가동 시간, 로드 애버리지를 돌려준다.
수집 방식을 결정한 제약이 둘이다.

- **`proot` 안의 `/proc`은 거짓을 말한다.** `/proc/stat`, `/proc/uptime`,
  `/proc/loadavg`는 정적이거나 조작된 값을 돌려준다. 가동 시간과 로드는 `ctypes`로
  `sysinfo(2)` 시스템 콜을 불러 얻고, CPU 사용률은 Termux 쪽에서 구한다.
- **배터리 값은 Termux:API에서 온다.** 즉 이 호출은 안드로이드 앱이 살아 있는지에 의존한다.
  배터리 필드가 없으면 0이 아니라 "알 수 없음"으로 취급한다.

![실시간 대시보드. 코어별 사용률, 메모리, 스왑, 배터리, 온도](images/shot-dashboard.png)

이 값을 쓰는 대시보드는 폰 사본에만 빌드된다. 공개 방문자의 브라우저가 내 폰을 찌르게 두면
안 된다([`02-web-server.ko.md`](02-web-server.ko.md)).

## 6.4 다운타임은 추측하지 않고 잰다

서로 다른 두 숫자를, 서로 다른 방법으로 잰다.

**계획된 재시작** — 프로브를 띄운 뒤 재시작하고 간격을 읽는다.

```bash
./measure_downtime.py --once &        # 기본 0.5초 간격
./start_services.sh restart
# downtime: 11.6 s   → downtime.log에 기록된다
```

쓸모 있는 옵션: `--local`은 공개 주소 대신 `127.0.0.1:8080`을 찌른다. `--interval`은
해상도와 요청 수를 맞바꾼다(ngrok 무료 플랜은 요청 수를 센다). `--once`는 한 번의
중단·복구 주기 뒤 끝난다.

**예기치 않은 중단** — 감독자마다 하트비트 파일을 유지하고 시작할 때 비교하므로, 아무도
보고 있지 않아도 간격이 원인과 함께 남는다.

```
Last Downtime: 168s (unexpected_shutdown_or_reboot, 2026-09-19 17:27:59 ~ 17:30:47 UTC)
```

"사이트가 떠 있었는가"를 묻는다면 로컬 포트가 아니라 공개 주소를 재야 한다. 빌드 교체를
0.3초에 끝낸 재시작도 터널에서는 12초를 쓸 수 있고, 그것은 밖에서 재야만 보인다.

## 6.5 폰을 익히지 않고 부하 시험하기

단계별 부하, 쿨다운, 클라이언트 스크립트가 담긴 전체 규격은
[`reference/STRESS_TEST_SPEC.md`](reference/STRESS_TEST_SPEC.md)에 있다. 숫자보다 구조가
중요하다.

- **부하는 PC에서 만든다.** 시험 대상 기기에서 돌리는 부하 생성기는 부하 생성기를 잰다.
- **Tailscale로 `100.x.y.z:8080`을 직접 때린다.** 그래야 ngrok 엣지와 내 업링크가 아니라
  폰을 재는 것이 된다.
- **단계마다 쿨다운을 넣어 올린다.** 그리고 단계마다 `/api/metrics`를 읽는다. 팬 없는
  기기에서 흥미로운 실패는 열이고, 열은 부하가 몇 분 지속된 뒤에야 나타난다.
- **오류가 아니라 온도로 중단한다.** 상한은 시작 전에 정한다.

## 6.6 테스트 돌리기

```bash
python3 tests/test_serve_blog.py      # 35개
python3 tests/test_private_docs.py    # 47개
```

둘 다 블랙박스다. 임시 디렉터리와 자체 포트에 자기 서버를 띄우므로, 운영 중인 폰에서 언제
돌려도 안전하다. 서버 파일을 고친 뒤에, 그리고 `publish` 전에 돌린다.

테스트가 실제로 무언가를 확인하는지 보려면 사본을 일부러 망가뜨린다.

```bash
cp serve_blog.py /tmp/x.py     # 사본에서 경로 검사를 지운다
# 6개가 실패해야 한다. 전부 통과하면 그 테스트는 장식이다.
```

## 6.7 일상 점검

**서비스를 제대로 멈춘다.** 비활성 플래그를 만들지 않으면 런처와 15분 작업이 방금 멈춘
것을 다시 띄운다.

```bash
touch /root/.services_disabled        # 블로그 + ngrok
touch /root/.private_docs_disabled    # 문서 뷰어
touch /root/.code_server_disabled     # code-server
./start_services.sh stop
# ... 점검 ...
rm /root/.services_disabled && ./start_services.sh start
```

**로그.** 로그는 모두 `/root/logs/`에 쌓인다. 폴더가 없으면 감독자가 만든다. 감독자는
각자 로그를 회전시킨다(블로그 10MB, 비공개 서비스 2MB, 배터리 감시 512KB). 방치해서 자라는 것은 없지만, `/root/blog_builds/`는 배포마다 디렉터리가 하나씩
쌓이므로 가끔 정리한다.

```bash
ls -1dt /root/blog_builds/* | tail -n +6 | xargs rm -rf
```

**이 넷은 백업한다.** 나머지는 이 저장소에서 다시 만들 수 있다.

| 무엇 | 이유 |
|:---|:---|
| 블로그 원본 저장소 | 내가 쓴 글이다. git에 있으니 push한다 |
| `~/.config/ngrok/ngrok.yml` | 토큰, 곧 내 고정 주소 |
| `/root/.config/code-server/tls/ca.key`와 `ca.crt` | CA를 잃으면 모든 기기에서 다시 신뢰시켜야 한다 |
| `/root/private_docs.list` | 내 허용 목록. 저장소에는 없다 |

**주 1회, 1분.** status 명령 셋, 배터리 로그 한 번, 배포 상태 확인이다.

```bash
./start_services.sh status && ./private_docs.sh status && ./code_server.sh status
tail -3 /root/logs/battery_watch.log
./publish_blog.sh status
```
